## Lenses

**1. Product fit and wiring (lead).** The CLI still wires every phase-1 command into `Inbox` (`src/cli/main.ts`), and the CLI constructs `new Inbox({ home })` without the new `store` option, so its open path (create, `ensureHome`, 5 s busy timeout, migrate) is unchanged. The informational workflow runs end to end on this snapshot (table above). `doctor` still reports the store, journal mode and schema. Producers now get the retry semantics spec §6.3 implies ("an identical update is a no-op").

**2. Correctness and edge cases (lead).** Probed the hash-first order through the real CLI, item with handoff and cwd in a folder containing a space and `ü`:

| Case | Result |
|---|---|
| Stale `--if-revision 1`, identical content to current rev 2 | `ok`, `changed:false`, rev 2 |
| Stale rev, only `profile_id` differs | `REVISION_CONFLICT` (profile is in the hashed payload) |
| Stale rev, only `title` differs | `REVISION_CONFLICT` |
| Stale rev, same JSON and path, handoff bytes changed on disk | `REVISION_CONFLICT` (hash covers handoff sha256) |
| Item archived, identical content, stale or current rev | `ITEM_IN_HISTORY` (archive check precedes the hash) |
| Blocking attempt present | `assertNoBlockingAttempt` still precedes the hash, so `ATTEMPT_IN_PROGRESS` wins over the no-op |
| Identity or kind changed | still refused before anything else (`INVALID_ITEM`) |
| Retry after `mark-read` | no-op keeps `read:true`, `read_revision` 2, `state_version` unchanged |
| A-B-A: rev 3 restores rev 1 content; stale `--if-revision 1` with rev 2 content | `REVISION_CONFLICT`; with rev 1 content: no-op (see N1) |
| `--if-revision 99` or `0` with identical content | no-op (see N2); `-1` is refused by the parser, exit 2 |

No stale or wrong caller slips past the archive, attempt, identity or kind checks; the only thing the hash can override is the revision guard, and only when the result would be byte-identical to what is stored.

**3. Data integrity.** The no-op path writes nothing: no revision, no `state_version` bump, no event, read and snooze state untouched (verified live and via `change_token`). Revisions stay immutable. The bridge's `existingOnly` open cannot create a stray empty store; it still runs the IMMEDIATE-transaction migration, so the schema stays consistent. `acceptPrompt`'s new `blocked` refusal only adds a refusal; it cannot accept or deliver anything new.

**4. Contracts and privacy.** CLI envelope and exit codes unchanged. `PromptRefusal` gains `ATTEMPT_BLOCKED`, internal to the bridge contract. Privacy: none found.

**5. Tests and evidence.** Both new tests fail if their code is removed or reverted (checked by reading the paths: the retry test hits `REVISION_CONFLICT` under the old order; the lock test needs `handoffReadError` wired into `captureHandoff`). No test pins that a stale caller with *different* content still conflicts after the reorder, but the pre-existing test at `core.test.ts:116` (`v3` on stale rev 1) does exactly that.

**6. Failure handling.** `HANDOFF_UNAVAILABLE` (retryable, exit 1) now proven through `submit`. The bridge's short busy timeout is scoped to hook opens; the CLI keeps its 5 s. A missing store on `existingOnly` maps to `STORE_ERROR`, not a crash. See N3 on the blocked-prompt refusal and recoverability.

**7. Simplicity and ownership.** Change is a two-line reorder plus a comment; core stays the only DB writer. `OpenOptions` lives in `db.ts`, used only by the bridge. No unasked scope inside M1.

## Notes

- **M0-R2-N1 (A-B-A no-op):** `src/core/inbox.ts:231`. If content goes A (rev 1), B (rev 2), A (rev 3), a stale caller sending A with `--if-revision 1` gets `changed:false` although someone else changed the item in between. The stored content equals what the caller asked for, so nothing is lost; the response carries `content_revision` 3, so a careful producer can see it. Acceptable; mention in the producer skill (INB-015) that `changed:false` means "the item now holds your content", not "nobody else touched it".
- **M0-R2-N2 (revision guard ignored on identical content):** `src/cli/main.ts:36`, `src/core/inbox.ts:231`. `--if-revision 0` or `99` with identical content now returns `ok` instead of `REVISION_CONFLICT`. Harmless (nothing changes), but a producer bug passing a nonsense revision goes unnoticed on that path. No action needed.
- **M0-R2-N3 (blocked attempt erases a late opening prompt):** `src/core/attempts.ts:498-500`. If a worker records a dispatch (`prompt_state` started) and then marks the attempt `blocked` (spec §13 readiness timeout, "mark uncertain/blocked"), a late-landing opening prompt is refused and erased by the hook, `prompt_state` stays `started`, and the intent log will not resend a started op; the attempt can then only be abandoned. Fail-closed, no false delivery, so no M1 break. Route to INB-006 / INB-009: after dispatch has started, a worker should mark `uncertain`, not `blocked`, or "continue" must account for an erased prompt. The INB-005 reviewer owns the bridge side.
- **M0-R2-N4 (decision not recorded):** `docs/decisions.md` "Build decisions" has no line for "an update whose content already matches the current revision is a no-op before the revision check". The commit message and INB-021 notes say it; one line in decisions.md would stop a later agent from re-arguing it.
