## Findings

### INB004-R2-F1: The stricter loadProfiles check has no test (Minor)
- **File:** `src/core/profiles.ts:38`, with no matching test in `test/unit/config.test.ts`.
- **Scenario:** revert line 38 to `win32.isAbsolute(p.claude_config_dir)`.
- **Expected:** a unit test fails. The fix's disposition says the change is "used for profile dirs in setup and load".
- **Actual:** by inspection, the suite stays green. No test writes a `profiles.json` with a root-relative or drive-relative `claude_config_dir`. The probe confirmed that the current code does refuse `\Users` and `C:Users` with PROFILE_NOT_CONFIGURED.
- **Impact:** low. The load-side guard could regress unnoticed, and the worker would then launch with a folder that depends on the current drive.
- **Smallest fix:** one test in the round 1 block. Write `{"profiles":{"work":{"agent":"claude-code","claude_config_dir":"\\Users"}}}` to `profilesPath(f.home)` and expect `loadProfiles(f.home)` to throw PROFILE_NOT_CONFIGURED.

### INB004-R2-N1: The README does not state the new rules (Note)
- **File:** `README.md:43` and `README.md:45-53`.
- The README says "Folders must be absolute". It does not say that only drive or UNC paths count, or that unknown `config.json` keys are refused rather than ignored.
- A one-line addition would stop a user from being surprised by a STORE_ERROR for a key they misspelt.

### INB004-R2-N2: One bad entry blocks every profile (Note)
- **File:** `src/core/profiles.ts:36-44`.
- An old `profiles.json` with one root-relative entry now makes `loadProfiles` throw for the whole file. So every `open` and `doctor`'s profile list fail, not just the bad profile.
- This is reachable only if the user gave such a path to the `d160fac` setup. It is loud, and the fix is to re-run `setup-profiles --force`.
- Acceptable as it is.

### INB004-R2-N3: Hand-written profile folders are not canonicalised on load (Note)
- **File:** `src/core/profiles.ts:45`.
- `canonicalDir` runs only on write. A hand-written `claude_config_dir` with a trailing `\` or forward slashes is handed to the launch unchanged.
- The fingerprint is still consistent: the probe found the same value from the raw form and the canonical form.
- The only remaining exposure is display, and the argv-quoting concern from round 1 F3, for hand-edited files only. Canonicalising in `loadProfiles` too would close it, if wanted.
