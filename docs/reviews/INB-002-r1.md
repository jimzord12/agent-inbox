**Unit:** INB-002, "Add handoff attempts with leases, fencing and receipt checks"

## Verdict: FINDINGS

There are two open Material findings, F1 and F2. Each lets the core accept a sequence that the spec forbids: a second protocol prompt in one attempt, or a delivery committed after the bridge reported that the bound session was replaced. Acceptance criteria 1–6 are otherwise met and tested.

## Findings

### INB002-R1-F1 — Material — a second opening prompt can be accepted after a "failed" dispatch is cleared
- **Where:** `src/core/attempts.ts:325-344` (`finishOp`, `clearFailedOp`) and `:311-323` (`beginOp`)
- **Scenario:**
  1. The worker calls `beginOp(dispatch_prompt)`.
  2. Herdr submits the prompt, and the `UserPromptSubmit` bridge calls `acceptPrompt`. `prompt_state` becomes `accepted`.
  3. The Herdr call then returns an error, and the worker records `finishOp(..., "failed")`. Because `prompt_state` is no longer `started`, the state stays `accepted` while the op says `failed`.
  4. On retry, `clearFailedOp` deletes the op even though `prompt_state = accepted`.
  5. `beginOp(dispatch_prompt)` succeeds again and overwrites `prompt_state` to `started`.
  6. The resent prompt passes `acceptPrompt` a second time. Probe result: `begin again: null started`, then `second accept: {"ok":true}`.
- **Expected:** spec §9.2 step 6 and §13 allow at most one automatic prompt submission per attempt. A resend is allowed only when a definitive rejection proves the prompt was not delivered. Bridge evidence of acceptance contradicts "definitive rejection".
- **Actual:** the evidence of acceptance is erased, and the guard accepts the duplicate.
- **Impact:** the handoff is pasted twice into the live session. The one-time acceptance guard, which the spec relies on because Herdr has no compare-and-send, is bypassed through core calls alone.
- **Smallest fix:** keep the "already accepted" evidence from ever being lost:
  - `clearFailedOp` refuses (`STATE_CONFLICT`) when `op = dispatch_prompt` and `prompt_state` is not `rejected`.
  - `beginOp(dispatch_prompt)` never moves `prompt_state` away from `accepted`.
  - Add a unit test for this sequence. There is currently no test of `clearFailedOp` or of the `rejected` path.

### INB002-R1-F2 — Material — `commitDelivery` succeeds over a bridge block saying the bound session was replaced
- **Where:** `src/core/attempts.ts:370-403`, together with `fencedWrite` at `:501-513`, which accepts every blocking status.
- **Scenario:**
  1. A valid receipt candidate is captured.
  2. Before the worker focuses and commits, the session is replaced, for example by `/clear` in the pane. A new `SessionStart` calls `bind` with a new session id.
  3. `bind` returns `RECEIPT_INVALID` and sets the attempt to `blocked`.
  4. The worker, still holding its generation, calls `commitDelivery`.
  5. The commit succeeds: the attempt becomes `succeeded`, the error is cleared, and the item is archived as `delivered`. Probe result: `rebind new session: {"ok":false,...} blocked`, then `commit: succeeded null delivered`.
- **Expected:**
  - Spec §6.2: `blocked` and `uncertain` need an explicit continue or reconcile step.
  - Spec §10.3: `/clear` or session replacement requires revalidation.
  - Spec §9.1: no delivery without the bound session.
- **Actual:** the core ignores the block it just recorded and commits.
- **Impact:** a false delivery is possible. The item goes to History as delivered, but the live conversation no longer holds the handoff. Only a worker-side Herdr occupant check (INB-006) would stand in the way; the core, which owns integrity, adds no guard.
- **Smallest fix:**
  - `commitDelivery` requires `a.status === "in_progress"`, so a block must first be cleared through an explicit retry (`resume`).
  - Add a unit test for the sequence above.
  - Optionally, a failed re-bind on an already-bound attempt could also clear `receipt_candidate_json`.

### INB002-R1-F3 — Minor — the worker can mark an attempt `failed` while an external op is still `started` or `uncertain`
- **Where:** `src/core/attempts.ts:358-360` and `:515-526`
- **Scenario:**
  1. `dispatch_prompt` is recorded `uncertain`.
  2. The worker calls `fail()`.
  3. The item is released, and a new `open` creates a second session. Probe result: `blocking after fail: null`, `new open reused: false`. The first session may already hold the prompt.
- **Expected:** spec §6.2 says `failed` means no unresolved side effect remains. Ending such an attempt is the user's explicit `abandon`.
- **Impact:** low today, since no worker exists yet, but this is a cheap core guard for INB-006 and INB-009.
- **Smallest fix:** `transition(..., "failed")` refuses (`STATE_CONFLICT`) when any `attempt_ops` row is `started` or `uncertain`. `abandon` stays unrestricted.

### INB002-R1-F4 — Minor — bridge results do not tell a protocol prompt from an ordinary user prompt
- **Where:** `src/core/attempts.ts:434-453` and `:485-492`
- **Scenario:**
  - In the launched session, every later ordinary user prompt reaches `acceptPrompt` and returns `{ok:false, reason:"not the expected opening prompt"}`.
  - After success or revocation, the call throws `RECEIPT_INVALID`.
  - A mismatched protocol prompt (wrong hash, duplicate) returns the same `ok:false` shape. The only difference is a free-text reason.
- **Expected:** spec §9.2 step 6 says to fail closed for the protocol prompt and let ordinary prompts continue. The INB-005 hook needs a stable signal for that choice.
- **Impact:** the hook must string-match reasons or duplicate the `[agent-inbox ` prefix logic. If it gets this wrong, it either blocks the owner's normal prompts or lets a bad protocol prompt through.
- **Smallest fix:** return a stable `protocol: boolean` (the prompt starts with `[agent-inbox <id>]`) and a reason code. Return `ok:false` with a code instead of throwing for a terminal or revoked attempt. Alternatively, record this as a must-have in INB-005.

### INB002-R1-F5 — Minor — rejected or late receipts leave no diagnostic
- **Where:** `src/core/attempts.ts:457-481` and `:485-492`
- **Scenario:** a `Stop` with a wrong challenge, or a late receipt for an abandoned attempt, returns `ok:false` or throws. Nothing is persisted.
- **Expected:** spec §13 says to reject an invalid or late receipt and record bounded diagnostics. §12.1 says the UI shows the error without log inspection.
- **Impact:** an attempt stuck at `await_receipt` shows no reason, so the owner cannot see that the model printed a bad marker.
- **Smallest fix:** on a rejection for a live attempt, store a bounded `last_receipt_rejection` (reason plus time, no message text) in the same transaction. For revoked attempts, an event with `attempt_id` and reason only.

### INB002-R1-F6 — Minor — the prompt guard does not check cwd
- **Where:** `src/core/attempts.ts:434-448`
- **Scenario:** `UserPromptSubmit` input includes `cwd`, and spec §9.2 step 6 lists cwd among the checks. `acceptPrompt` takes no cwd, so it cannot compare against the bound cwd.
- **Impact:** low, because the session id and capability already pin the session.
- **Smallest fix:** add a `cwd` parameter and compare it with `normalizeDir` against `a.cwd`.

### INB002-R1-F7 — Note — the packet path can change after dispatch
- **Where:** `src/core/attempts.ts:296-298`
- `setPacketPath` stays writable after `dispatch_prompt` began or was accepted (probe result: still `accepted` after a path change). That would make the stored expected prompt differ from what the session read. Consider refusing once `prompt_state` is not `none`.

### INB002-R1-F8 — Note — the binding has no Herdr target
- **Where:** `src/core/attempts.ts:108-114`
- Spec §9.1 step 2 includes the Herdr target in the binding. The binding records session id, cwd, config dir and auth-env names only. Preflight shows that `agent.get` reports the native session UUID, so the worker can verify the target. Record which side owns this check when INB-006 is built.

### INB002-R1-F9 — Note — the receipt does not check for a "waiting" statement
- **Where:** `src/core/attempts.ts:592-623`
- `parseReadyMarker` requires a non-empty orientation but no "waiting" statement (spec §9.1 step 4). Being relaxed here is reasonable; the docs should say the check is intentionally loose.

## Lenses

**1. Product fit and wiring — no findings.**
- `Attempts` is not reachable from the CLI yet. Wiring `open`, `attempt`, `retry`, `abandon` and `focus` belongs to INB-006 and INB-008 on the board, so this is expected.
- Criteria 1–6 are each covered by `test/unit/attempts.test.ts`:
  - AC1: lines 79–97.
  - AC2: lines 127–137 and 283–289.
  - AC3: lines 171–191.
  - AC4: lines 205–219.
  - AC5: lines 221–254.
  - AC6: lines 267–300.
- Gaps against what later tasks need are F4 and F8.

**2. Correctness and edge cases — F6, F7.**
- `open` returns the existing blocking attempt before the history and revision checks, so duplicate clicks are idempotent. The partial unique index `attempts_one_blocking` (`migrations.ts:104`) enforces one blocking attempt at the database level.
- Lease expiry compares fixed-width ISO strings, which order correctly.
- Directory normalisation is case- and slash-insensitive, which is right for Windows.
- `session_uuid` is unique.
- The ready-marker parser is strict about keys and types, and the marker must be on the last line.

**3. Data integrity (lead) — F1, F2.**
- Delivery commits receipt, `succeeded`, archive(`delivered`), the `state_version` bump and both events in one IMMEDIATE transaction (`fencedWrite` → `inbox.write`).
- While an attempt is blocking, the item is frozen: snooze, unsnooze, archive, restore and update are refused (`inbox.ts:224, 392, 404, 418, 433`), so a receipt cannot archive a newer revision.
- `ALREADY_DELIVERED` and `--fresh` keep the earlier succeeded attempt unchanged.
- Packet bytes and hash are stored in the attempt row before any file exists.
- The two gaps are the duplicate-prompt path (F1) and the commit over a block (F2).

**4. Contracts and privacy — F4. Privacy check: none found.**
- `AttemptView` leaves out the capability, the challenge and the packet bytes, and a test checks that the challenge is absent.
- Event metadata carries no secrets or handoff text.
- The challenge appears in the packet but not in the opening prompt (§9.2 step 2).

**5. Tests and evidence — no separate finding.**
- Tests exercise real SQLite and mock only the clock.
- Deleting the unique index, the fencing check or the bridge checks would fail the existing tests.
- Missing tests are folded into F1 and F2: the `clearFailedOp` / `rejected` path, `resume`, and commit from `blocked` or `uncertain`.

**6. Failure handling (lead) — F1, F2, F3, F5.**
- The intent log is sound: `beginOp` returns the earlier state instead of starting an op again.
- Lease expiry fences the old worker, and a takeover does not repeat ops.
- `abandon` revokes the attempt, bumps the generation, keeps the session reference and frees the item for a new session UUID.
- A lost dispatch result becomes `uncertain`.

**7. Simplicity and ownership — no findings.**
- All writes go through core `Inbox.write`, and `attempts.ts` is the only attempt writer.
- `profiles.ts` is a minimal user-owned config. No unasked scope inside the unit.

**8. Repository and docs — no findings.**
- The commit subject and scope match the change.
- The task is `In Review` with a plan. The board diff is uncommitted, which is normal mid-loop.
- `docs/decisions.md` lists `uncertain` under release C while the code already ships it. That is consistent, since the code goes beyond the plan without contradicting it.
