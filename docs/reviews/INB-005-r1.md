## Lenses

**1. Product fit and wiring.** Pass.
- AC1: `writeBridgeSettings` writes `bridge.json` (home, attempt id, capability) and `settings.json` holding the three hooks in exec form, with a 15 s timeout and no matcher. The capability is not in `settings.json`, and a test asserts that.
- AC2: the three startup checks behave as follows.

| Case at startup | Result |
|---|---|
| Wrong session id or wrong cwd | attempt `blocked` with `RECEIPT_INVALID` |
| Wrong config dir or an auth variable present | attempt `blocked` with `PROFILE_LAUNCH_UNSUPPORTED` |
| Any startup mismatch | no binding is written, so the guard later refuses with `NOT_BOUND` |

- AC3 and AC4 are met through `acceptPrompt` and `captureReceipt`.
- AC5 holds: the deadline is under the settings timeout, output is limited to error codes, and probes and tests confirm both.
- The worker that calls `writeBridgeSettings` is INB-006, as the brief states.

**2. Correctness and edge cases.** Pass with notes.
- With no matcher, SessionStart also runs on `clear` and `fork`. Both carry a new session id, so the attempt is blocked and its receipt candidate dropped. On `compact` and `resume` the id is the same, so the attempt binds again without effect.
- `normalizeDir` handles mixed slashes and letter case. It does not handle 8.3 short paths or junctions; INB-007 should confirm what cwd Claude reports.
- Exec form keeps paths with spaces and Unicode intact.
- See N2 (the guard accepts on a `blocked` attempt) and N3 (the auth variable list).

**3. Data integrity.** Pass.
- None of the failure paths can mark an attempt delivered. A crashed, cancelled or busy hook leaves `prompt_state` short of `accepted`, so `captureReceipt` refuses and `commitDelivery` refuses.
- F2 covers the one case where real evidence can be lost.

**4. Contracts and privacy (lead).** Pass.
- **Hook shape.** Exec form, the `timeout` in seconds and the `hooks: { Event: [{ hooks: [{ type, command, args, timeout }] }] }` layout match the docs.
- **Inputs read.** The hooks read `session_id`, `cwd`, `prompt` and `last_assistant_message`, the fields the docs name.
- **Pass path.** It prints nothing on exit 0. That matters: SessionStart and UserPromptSubmit stdout would otherwise become context Claude sees.
- **Block path.** Exit 2 with a stderr line carrying only a code (for example `opening prompt refused (STORE_BUSY)`). The capability, challenge, packet text and environment values are never printed. Tests check this for the capability and challenge, and the auth-env case checks a fake key value.
- **Stored binding.** It holds the session id, cwd, config dir path and the names of auth variables only.
- **Privacy:** none found.

**5. Tests and evidence.** Pass.
- The tests run the real hook process with real stdin and exit codes. Mocking stops at the true boundary: Claude's hook input is built by hand.
- Deleting any one handler makes a test fail: binding, the profile and auth block, the `/clear` block, single acceptance, ordinary-prompt pass, the unusable-store paths, deadline behaviour, and Stop candidate versus no candidate.
- Gaps: no test holds the store busy (the probe covered that), and none covers a home that does not exist (F3).

**6. Failure handling (lead).** Pass with three Minor findings. Every failure path, by what Claude then does:

| Path | Hook result | What Claude does | Can it block the owner's ordinary prompt? |
|---|---|---|---|
| Bridge file missing or broken; attempt unknown, wrong capability or closed | exit 0; protocol prompt exit 2 | ordinary prompt passes, protocol prompt blocked | No |
| Store busy (probe: about 5.5 s, then `STORE_BUSY`) | protocol exit 2 / ordinary exit 0 / stop exit 0 | as stated; the ordinary prompt is delayed about 5.5 s | No, delay only |
| Stdin not read within 10 s | exit 2 for every prompt | prompt blocked; the block message repeats it, so it is not lost | Yes, by design, and only if Claude never closes stdin (N4) |
| Hook cancelled at 15 s, exits 1, or cannot start (missing script or Bun) | no decision | **prompt proceeds, including a protocol prompt** (fails open) | No |
| SessionStart or Stop fails in any way | exit 0 | session carries on | n/a |

The fail-open row is a Claude platform property, not a code bug. When it happens, acceptance is never recorded, so the attempt cannot deliver and stays recoverable by abandoning it. INB-006 must treat "dispatched but not accepted" as uncertain (§13). F1 covers how close the real runtime comes to the 15 s cancel.

**7. Simplicity and ownership.** Pass.
- The bridge writes only through `Attempts` in core.
- `looksLikeProtocol` duplicates the prefix test inside `acceptPrompt`. That is acceptable, because it has to work without the store.
- No unasked scope.

**8. Repository and docs.** Pass.
- The commit scope matches the task. The implementation notes state the hook facts and what is unverified, in line with preflight §7.
- `SessionEnd` and `StopFailure` are not hooked. Spec §9.2 step 3 says "as supported", and the AC lists only three events (N5).

## Findings

### INB005-R1-F1: Minor. The 10 s deadline cannot interrupt a store that is hung or busy
- **Where:** `src/bridge/main.ts:10` and `:42-48`, `src/core/db.ts:5`, `src/bridge/hooks.ts:67`.
- **Scenario:** a hook opens the store, which runs an IMMEDIATE migrate transaction that can wait up to 5 s busy. It then runs an IMMEDIATE write that can wait up to another 5 s. Both waits are synchronous, so the `setTimeout` deadline cannot fire during them. It only bounds the stdin read.
- **Expected:** the comment's promise holds: "a hung store or disk never holds the session; at the deadline a protocol prompt is blocked".
- **Actual:** the real bound is Bun start-up plus up to about 10 s of busy waiting (the probe measured 5.5 s for one wait). That leaves roughly 4 s before Claude's 15 s cancel. A synchronous read of the bridge file on a hung disk is not bounded at all. Past 15 s, Claude cancels the hook and the protocol prompt goes through unguarded.
- **Impact:** low. No false delivery, because acceptance is never recorded. But the margin is thin on a loaded machine, and it breaks silently if `BUSY_TIMEOUT_MS` is ever raised.
- **Smallest fix:** open the store from the hooks with a shorter busy timeout (for example 2 s), or raise `HOOK_TIMEOUT_SECONDS` to 30 (Claude's own default for UserPromptSubmit). Then correct the comment to name the real bound.

### INB005-R1-F2: Minor. A valid acknowledgment is dropped silently when the store is busy at Stop
- **Where:** `src/bridge/hooks.ts:89`, `:110-116`.
- **Scenario:** the session ends its opening turn with a valid `INBOX_READY_V1` marker while the worker or the CLI holds the write lock for more than 5 s.
- **Expected:** the candidate is persisted, or the failure is left somewhere a reconcile can see it (lens 6, "loud").
- **Actual:** `captureReceipt` throws `STORE_BUSY`, `failClosed` returns exit 0, and nothing is recorded anywhere (probe "stop while locked": exit 0 after 5.5 s, no candidate). Claude will not run Stop again for that turn.
- **Impact:** the item stays Active and can only be recovered by abandoning it. A new session then re-receives context the old one already acknowledged. Rare, but invisible.
- **Smallest fix:** in the stop path, retry `captureReceipt` on `STORE_BUSY` until the deadline. If it still fails, write the raw `last_assistant_message` marker line to a `receipt-pending.json` beside `bridge.json` for INB-009 to reconcile.

### INB005-R1-F3: Minor. A hook recreates a store at a home that no longer exists
- **Where:** `src/bridge/hooks.ts:67` through `new Inbox` → `ensureHome`, `src/core/home.ts:17-18`, `openStore` with `create: true`.
- **Scenario:** a session outlives its inbox home. Examples: a live-evaluation home deleted after the run, or `AGENT_INBOX_HOME` moved. The owner then sends an ordinary prompt in that session.
- **Expected:** the hook passes and leaves the disk alone.
- **Actual:** the probe shows the hook exits 0 but creates `<home>\inbox.db` with the full schema. It does so again on every prompt or Stop.
- **Impact:** low. Stray stores appear in deleted test homes, and could appear at a real path, which can confuse `doctor` or later runs.
- **Smallest fix:** in `handle`, fail closed if `dbPath(ctx.home)` does not exist, before constructing `Inbox`. Better still, give `Inbox` an open-existing-only option for the bridge.

## Notes (do not block)

- **N1. Hook script path.** The hook command is `process.execPath` plus `import.meta.dir/main.ts` (`src/bridge/settings.ts:38-39`). Under a compiled or installed build (INB-020), either path may be virtual or point at a moving checkout. A missing script makes Bun exit 1, which is the fail-open row above. INB-006 and INB-020 should pin a stable script path.
- **N2. The guard accepts on a `blocked` attempt.** `acceptPrompt` refuses only closed attempts, so a `blocked` attempt that is still bound to the right session would accept (`src/core/attempts.ts:484-506`). No live path reaches this today, since the worker never dispatches a blocked attempt. Refusing any status other than `in_progress` in the guard would be cheap defence in depth.
- **N3. Auth variable list** (`src/bridge/hooks.ts:33-41`).
  - **Possible gap:** `ANTHROPIC_CUSTOM_HEADERS` can carry credentials and is not on the list.
  - **False positive:** values such as `CLAUDE_CODE_USE_BEDROCK=0` count as set. That fails loud, which is safe.
  - **Narrower than the preflight:** preflight §4 says the binding records which `ANTHROPIC_*` / `CLAUDE_CODE_*` names are present. The code records only the listed names. This is fine for the MVP; the INB-007 environment check decides whether to widen it.
- **N4. Ordinary prompts can be blocked by design.** The stdin-timeout path blocks an ordinary prompt (the test at `test/unit/bridge.test.ts:176-196` codifies it). Per the docs, the block message repeats the original prompt, so the owner loses nothing but a resend. This is acceptable.
- **N5. No Stop check for subagents, and no end hooks.**
  - Stop has no `agent_id` check. The docs say Stop is main-agent only, so this is fine; asserting that `agent_id` is absent would be cheap insurance.
  - `SessionEnd` and `StopFailure` are not hooked. Left to INB-011 (availability) and INB-007.
