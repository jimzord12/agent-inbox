## Targeted questions

**(a) Can one handoff be accepted twice?**
- Within one attempt: no. Acceptance needs `prompt_state` to be `started` or `uncertain`, and `accepted` is never left (`:502-504`).
- Across attempts: the partial unique index (`migrations.ts:104`) and `ALREADY_DELIVERED` (`:169-178`) hold.
- One worker-misuse path remains: `fail` after the prompt was already accepted. See R3-F1.

**(b) Can delivery happen without the bound session's valid receipt?**
- No. `commitDelivery` requires all of:
  - status `in_progress`
  - a binding
  - `prompt_state = accepted`
  - a candidate, captured only from `session_uuid` with all five fields matching
  - the current revision, not archived
- Probe P6: a new worker takes over after an expired lease and marks the dispatch uncertain. A late bridge acceptance and receipt arrive. Commit is refused while the attempt is `uncertain`, and succeeds after `resume`. This is the reconcile path spec §9.2 and §13 intend.

**(c) Can a wrong-session or wrong-attempt protocol prompt get through?**
- No, for any prompt that begins with the prefix.
- A prompt with text before the prefix (for example `hi\n[agent-inbox …`) is `NOT_PROTOCOL`. That is acceptable: Herdr's agent send does not prepend text, and the prompt still names a foreign attempt id, so it cannot be accepted.

**(d) Can an item be released while a side effect is unresolved?**
- `fail` is now guarded on both the open ops and `prompt_state`.
- `abandon` releases the item unconditionally, by design (spec §13).
- See R3-F1 for the accepted-but-unreceipted case.

**(e) Can an attempt be wedged so neither resume nor abandon recovers it?**
- No. `abandon` needs only a blocking status, with no lease or fencing check, so every blocking attempt can be abandoned.
- The states with no forward step all have abandon as their exit:
  - an uncertain dispatch with no bridge evidence
  - a confirmed dispatch whose prompt the bridge never saw
  - a binding refused for the wrong profile
- This is the fail-safe behaviour the spec asks for.

## Findings

### INB002-R3-F1 — Minor — `fail` is allowed after the bridge accepted the opening prompt, releasing the item while that session holds the handoff
- **Where:** `src/core/attempts.ts:589-596` (the `transition` guard), together with `:357-364`.
- **Scenario (probe P1):**
  1. `beginOp(dispatch_prompt)`.
  2. The bridge accepts the prompt, so `prompt_state` becomes `accepted`.
  3. Herdr answers with an error, and the worker calls `finishOp(dispatch_prompt, "failed")`. The op becomes `failed`; `prompt_state` stays `accepted`, which is correct.
  4. The worker calls `fail(…, "HERDR_SEND_FAILED")`. This succeeds:
     - the status becomes `failed` and the attempt is revoked;
     - the item has no blocking attempt;
     - `open` creates a second attempt for the same revision.
  - The same happens when a valid receipt candidate already exists: it is discarded without a word.
- **Expected:**
  - Spec §6.2 says `failed` means "ended without delivery and no unresolved side effect remains".
  - Spec §13, "Prompt send response lost", says to check accepted-prompt and receipt evidence.
  - With the prompt accepted, the context is already in session A and its acknowledgment may still be coming. The worker path should not be able to end the attempt as "not delivered" and invite a second session.
  - The legitimate case, "target closes before successful handoff, fail only when closure is established", stays possible through `abandon`, or through an explicit closure flag.
- **Actual:** the guard checks only `started` or `uncertain` ops and the `started` or `uncertain` prompt states. `accepted` passes.
- **Impact:**
  - Reachable only through a worker that reacts to a Herdr error without reading the evidence. INB-006 and INB-008 do not exist yet.
  - The result would be duplicate work in two sessions, with the first session's valid receipt thrown away.
  - No false delivery is possible.
- **Smallest fix:**
  - In `transition` for `failed`, also refuse when `prompt_state = 'accepted'`, with a message such as "the session received the handoff; await the receipt, block, or abandon".
  - Or allow it only with an explicit `closureEstablished` argument that INB-011 sets.
  - Add one test.

### INB002-R3-N1 — Note — `commitDelivery` does not check the `focus` op
- **Where:** `src/core/attempts.ts:405-441`.
- **Probe P3:** with the `focus` op still `started`, `commitDelivery(…, {})` succeeds.
- **Why it matters:** spec §9.1 step 6 requires a successful focus before the commit. Today the core trusts the caller's `focus` argument. AC6 does not require the check, so this is the worker's job in INB-006.
- **Suggested fix:** INB-006 commits only after `finishOp(focus, "confirmed")`. Optionally, the core could refuse while a `focus` op is `started` or `uncertain`.

### INB002-R3-N2 — Note — a reconciled dispatch op stays `uncertain` on a delivered attempt
- **Where:** `src/core/attempts.ts:504` (acceptance does not touch `attempt_ops`).
- **Probe P6:** after a late acceptance and delivery, the view shows `ops: [["dispatch_prompt","uncertain"]]` beside `prompt_state: accepted` and `succeeded`.
- **Why it matters:** this is harmless, and `prompt_state` is the real evidence. INB-013 should show `prompt_state` rather than the raw op state, or acceptance could also mark an uncertain dispatch op `confirmed`.

### INB002-R3-N3 — Note — one test name claims more than it checks
- **Where:** `test/unit/attempts.test.ts`, test "resume and delivery clear the last rejection".
- **Problem:** the test checks only `resume`. Clearing on delivery has no test of its own: in the tested path the value is already null after `resume`.
- **Suggested fix:** rename the test, or add a delivery case where a rejection is recorded while the attempt stays `in_progress`, for example a mismatched ready marker followed by a valid one.
