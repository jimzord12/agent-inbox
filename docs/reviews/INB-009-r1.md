## Lenses

1. **Product fit and wiring** - Reconcile runs before get, list, status, open, attempt, retry and focus (`src/cli/main.ts` `RECONCILES`, inside `lazyInbox`). The CLI test kills deletion M12. All five ACs have code and a test. AC2 is met the cautious way: candidates are recorded, never adopted, and the attempt stays uncertain. That is correct, because no session can be bound to an orphan tab.
2. **Correctness and edge cases** - Fencing holds. Every reconcile write goes through `claim` plus a fenced write, and a second reconciler or a revived worker fails with STATE_CONFLICT. One narrow race is in N1: status is checked outside the claim's transaction. The label suffix match is sound: `tabLabel` always ends in ` <last 6 of id>`.
3. **Data integrity (lead)** - The commit shortcut is sound as written. It needs a confirmed focus, an accepted prompt and a receipt candidate, all under a fresh claim, and `commitDelivery` re-checks binding, acceptance, receipt and item state in one transaction. The item cannot move while a blocking attempt exists (`assertNoBlockingAttempt`). A live worker is never claimed: `claim` refuses a live lease even with the `leaseLive` pre-check deleted (M2 is equivalent). Blocked and uncertain attempts are never claimed (M10 killed). The defect: a pending receipt can bring back evidence the core dropped on purpose (F1). The guard that keeps the shortcut from committing without a confirmed focus is untested (F2).
4. **Contracts and privacy** - No CLI JSON shape changed. `ReconcileResult` is internal and not emitted. The pending file is read with the shape the bridge writes (`attempt_id`, `session_id`, `last_assistant_message`, `written_at`). The fake's `tab list` matches the adapter's `tabs()` (`{tabs: TabInfo[]}`). Privacy: none found.
5. **Tests and evidence (deletion probes)** - Killed: M3, M9, M10, M12, M14, M15. Survived but equivalent or backstopped: M1 (revoked implies failed), M2 (claim refuses a live lease), M4 (post-claim race guard), M5 and M6 (`commitDelivery` re-checks). Survived and not covered: M7 (focus state, F2), M8 (busy store keeps the pending file, F3), M11 (lease release, F6), M13 (orphan label filter, F6).
6. **Failure handling (lead)** - A busy store keeps the pending file and replays it later (P6, correct today). A non-InboxError inside reconcile fails the whole read command (F4). With a busy store, the read stalls about one busy timeout per lapsed attempt (F5). The extra cost per read is otherwise small: one `existsSync` plus a row and an ops read per unfinished attempt, and no writes in steady state.
7. **Simplicity and ownership** - All DB writes go through `Attempts` (the core). Reconcile sits in `src/worker`, next to the worker whose crash it handles. The worker change is small and scoped. No unasked scope.
8. **Repository and docs** - Commit subject and scope follow the convention. The task notes record the design choices (never claim blocked or uncertain, never restart a no-op attempt). The task is In Review with ACs unchecked, as expected before PASS.

## Findings

### INB009-R1-F1 - Material - Replay revives a receipt that bind deliberately dropped

- **Where:** `src/worker/reconcile.ts:68-95` (`replayPending`), against `src/core/attempts.ts:476-484` (`bind` clears `receipt_candidate_json` on a session mismatch).
- **Scenario (probe P3):**
  1. The session acknowledges. Stop meets a busy store, and the bridge writes `receipt-pending.json`.
  2. The pane's conversation is replaced (`/clear`: a SessionStart with a new session id). `bind` blocks the attempt `RECEIPT_INVALID` and nulls the receipt candidate, "so only a new, valid acknowledgment can deliver".
  3. The next `list` runs reconcile.
- **Expected:** the stale pending file is discarded, or at least does not restore the candidate.
- **Actual:** `replayed=1 status=blocked receipt_candidate=true`. The old acknowledgment is back.
- **Impact:** This breaks the core's receipt-invalidation rule (spec §9.2, superseded reports are rejected; §10.3, `/clear` requires revalidation). Delivery still needs a later retry in which Herdr reports the original session id in the pane, so a false delivery needs a second failure. One layer of the defence is gone, though, on exactly the path the pending file exists for.
- **Smallest fix:** discard the pending file when a bind-stage rejection is newer than its `written_at`. Or have the bind-mismatch path remove `receipt-pending.json`, or record a "receipt dropped at" time that replay compares against. Add a test for this sequence.

### INB009-R1-F2 - Material - The focus guard of the commit shortcut is untested

- **Where:** `src/worker/reconcile.ts:49` (`focus?.state === "confirmed"`).
- **Scenario (deletion probe M7):** replace the condition with `!!focus` (any focus op, including `started` or `uncertain`). All tests still pass.
- **Expected:** a test fails. With the mutant, a worker that died during the `herdr focus` call (op `started`), with an accepted prompt and a receipt candidate, would be committed as delivered without a confirmed focus.
- **Actual:** no test covers "focus started or uncertain, lease lapsed". `commitDelivery` does not check focus, so nothing else catches it.
- **Impact:** the only guard that keeps reconcile from committing without step 6 of spec §9.1 ("the adapter successfully focuses its verified pane") can regress silently.
- **Smallest fix:** a test where the focus op is `started` (and one where it is `uncertain`), the lease is lapsed and all other evidence is present. Expect `marked_uncertain`, with no delivery and the item still Active.

### INB009-R1-F3 - Material - The busy-store branch of replay is untested

- **Where:** `src/worker/reconcile.ts:91-93` (`if (... err.code === "STORE_BUSY") return false;`).
- **Scenario (deletion probe M8):** drop the early return, so a busy store falls through to `rmSync`. All tests still pass.
- **Expected:** a test fails. The pending file exists only because the store was busy at Stop. Deleting it during a second busy spell loses the acknowledgment for good, and Claude never re-runs Stop.
- **Actual:** behaviour is correct today (probe P6: file kept while busy, replayed on the next reconcile), but nothing pins it. The AC3 test only replays against a free store.
- **Smallest fix:** a test that holds a write lock from a second connection (as P6 does, with a short busy timeout). Expect the file kept and `receipts_replayed` 0, then 1 once the lock is released.

### INB009-R1-F4 - Minor - A non-inbox error inside reconcile fails every read command

- **Where:** `src/worker/reconcile.ts:58-61` (only `InboxError` is swallowed), `:76-87` (`rmSync`, `readFileSync`), `:50` (`JSON.parse(focus.detail_json)`).
- **Scenario (probes P1, P2):**
  - `receipt-pending.json` that cannot be removed: `rmSync` throws `ERR_FS_EISDIR`.
  - A focus detail that does not parse: `SyntaxError`.
  - Realistic trigger on Windows: a transient `EBUSY` or `EPERM` on delete, for example antivirus holding the just-renamed file.
  - In every case reconcile throws, and because it runs inside `lazyInbox`, `list`, `get`, `status`, `open`, `retry` and `focus` all answer INTERNAL.
- **Expected:** the module's own contract, "Reconcile never breaks a read". One attempt's housekeeping should be skipped and logged.
- **Actual:** the whole command fails, for every item, until the cause clears.
- **Impact:** a transient trigger costs one failed poll. A persistent one hides the inbox; only `abandon` and `events` still work.
- **Smallest fix:** in the per-attempt `catch`, swallow every error (optionally write one line to the attempt's `worker.log`). Wrap `rmSync` in its own try.

### INB009-R1-F5 - Minor - A busy store stalls each read by one busy timeout per lapsed attempt

- **Where:** `src/worker/reconcile.ts:36-62` (the loop carries on after STORE_BUSY).
- **Scenario (probe P5):** another connection holds a write lock, and three attempts have lapsed leases with ops recorded. `reconcile` returned after **16.3 s**, having claimed nothing. One attempt with a pending file took 10.9 s (P6): about 5 s for replay plus 5 s for the claim.
- **Expected:** a read command that waits at most about one busy timeout (spec §7, bounded busy handling, default 5 s). In WAL the read itself would not wait at all.
- **Actual:** the wait is N × 5 s. The mod polls `list`, so it can hit its own timeout.
- **Smallest fix:** stop the loop at the first STORE_BUSY (`break`), leaving the rest for the next read.

### INB009-R1-F6 - Minor - Lease release and the orphan label filter are untested

- **Where:** `src/worker/reconcile.ts:55` (`at.release` in `finally`); `src/worker/worker.ts:292` (`.filter((t) => t.label.endsWith(suffix))`).
- **Scenario:** deletion probes M11 and M13 both survive.
  - Without the release, reconcile's 30 s lease stays live. The very `retry` that just reconciled would then see a live lease and answer `started: false`, starting no worker.
  - Without the filter, every tab in the inbox workspace is named as an orphan of this attempt. The test has only one tab.
- **Smallest fix:**
  - Assert `lease_owner` is null after reconcile in the "died mid-way" test.
  - Add a second, unrelated tab to the lost-tab-create test and assert it is not a candidate.

## Notes

- **N1 (race, Note).** Reconcile reads `status === "in_progress"`, then calls `claim`, which also accepts `blocked`. If the worker records its own `AGENT_BLOCKED` between the two, while its lease has lapsed (machine sleep), the claim bumps the generation and fences the dialog watcher. That is the INB-006 r3 N2 case through a narrow window. `fresh.status` is re-checked, so nothing is overwritten, but the watcher is lost. A claim conditioned on `in_progress` inside the same transaction closes it.
- **N2 (Note).** Every reconcile uses the same lease owner, `"reconcile"`, so two concurrent reconcilers can claim over each other's live lease. Fencing makes this harmless. A per-process owner (`reconcile:<pid>`) would make the lease mean what it says.
- **N3 (Note).** `orphanTabs` lists tabs on the configured socket (`this.d.herdr`), not on the attempt's recorded `herdr_session`. If the config changed in between, the candidate list comes from another server. It is advisory only, so not a safety issue.
- **N4 (Note).** When the machine wakes from sleep, the mod's next `list` can find a live worker's lease lapsed and mark the attempt uncertain before the worker renews. That is recoverable by retry and consistent with spec §7 and §13. Similarly, when reconcile commits during `retry` or `open`, the user gets STATE_CONFLICT ("succeeded; nothing to retry") or ALREADY_DELIVERED rather than a success. The data is correct, but the message may surprise.
