## Lens 1. Product fit and wiring

I checked that every spec §8 command in this unit's scope exists in `COMMANDS` and reaches the core. `open`, `attempt`, `retry`, `abandon` and `focus` belong to later tasks.

**Criterion 9.** The spec does not separate producer and user commands by authentication. §8 says producers are not authenticated principals, and it asks only that internal commands be kept apart from the producer surface, with no public `set-delivered` command. How the code enforces it:
- The producer surface is `submit`, `update`, `get`, `list`, `events` and `status`.
- None of these can archive, set `archive_reason`, set `read_revision` or set `snoozed_until`.
- `update` makes new content unread by raising `content_revision`. It never touches `read_revision`, which is the behaviour spec §6.3 intends.
- No command declares delivery. The only `archive_reason='delivered'` write is in `attempts.ts:395`, the INB-002 receipt path.
- The user commands (`mark-read`, `snooze`, `archive`, …) can be called by any same-user process. That matches the spec's same-user trust model.

No findings beyond Note N1.

Findings: F1, F2, F3, F4.

### INB001-R1-F1 Minor: `mark-unread` on an updated item emits a redundant event
- **Where:** `src/core/inbox.ts:351`
- **Scenario:**
  1. The user reads revision 1, so `read_revision=1`.
  2. The producer updates the item to revision 2. The item is now unread.
  3. The user, or the mod, sends `mark-unread`.
- **Expected:** a no-op, because the item is already unread (`read_revision != content_revision`).
- **Actual:** the no-op check tests `read_revision === null`. So it raises `state_version`, writes `read_revision=NULL` and emits `item.read_changed {read:false}`.
- **Impact:** a spurious event for poll consumers. A second interface holding the old `state_version` gets a needless `STATE_CONFLICT` on its next archive or snooze.
- **Smallest fix:** `if (item.read_revision !== item.content_revision) return this.toView(item);`

### INB001-R1-F2 Minor: an event cursor ahead of the store is accepted silently
- **Where:** `src/core/inbox.ts:328` and `src/core/inbox.ts:625-628`
- **Scenario:**
  1. A producer holds cursor `500`.
  2. The store is restored from a backup whose latest sequence number is 300. Or the producer passes a cursor taken from another inbox home.
- **Expected:** the consumer is told its cursor is not valid for this store.
- **Actual:** every poll returns `next_cursor: "500"` and no events. New events take sequence numbers 301-500 and are skipped for good. `AUTOINCREMENT` continues from the restored `sqlite_sequence`.
- **Impact:** a producer silently misses events after a backup restore (spec §15, "backup/restore … preserve … events").
- **Smallest fix:** in `events()`, if `after > latestSeq()`, return `INVALID_ARGUMENT` (or `STATE_CONFLICT`) with `details.latest_cursor`, so the consumer can reset on purpose.

### INB001-R1-F3 Minor: `--until` accepts impossible calendar dates and rolls them over
- **Where:** `src/core/clock.ts:16-22`
- **Scenario:** `snooze ITEM --until 2026-02-30T09:00:00+02:00 …`
- **Expected:** exit 2 `INVALID_ARGUMENT`, as for other malformed times.
- **Actual:** Bun's `Date` turns it into 2026-03-02, and the item is snoozed to a date the user never typed. Probe 3 showed this. An `HH` of 24 also rolls over to the next day.
- **Impact:** low. It needs a typo, and the mod's picker probably builds valid dates.
- **Smallest fix:** after parsing, compare the year, month and day of the input text with the date shifted by the input's offset, and reject on a mismatch. Or reject `hh>23` and check `dd` against the month's length.

### INB001-R1-F4 Minor: a leading BOM is dropped from `handoff_text`, so it no longer matches the retained bytes
- **Where:** `src/core/inbox.ts:125` and `src/core/inbox.ts:264`; the same thing happens in `attempts.ts:184`
- **Scenario:** a producer's handoff file starts with a UTF-8 BOM, which is common for files written by Windows tools.
- **Expected:** spec §5.1 says the inbox retains the exact text bytes. `get --include-context` should give text whose UTF-8 encoding matches `handoff.sha256` and `handoff.bytes`.
- **Actual:** `new TextDecoder()` strips the BOM by default. Probe 1 returned no leading U+FEFF, while `bytes` counts it.
- **Impact:** small. A client that re-hashes the text to check it against `sha256` gets a mismatch. The packet also differs from the stored bytes by 3 bytes. The stored bytes themselves are intact.
- **Smallest fix:** use `new TextDecoder("utf-8", { ignoreBOM: true })` in both places. Or document that the BOM is dropped and check the hash against the bytes.

## Lens 3. Data integrity (lead)

What I checked:
- **Transactions.** Every mutation runs in one IMMEDIATE transaction, and its event is written in that same transaction.
- **Revisions.** They are immutable rows (PK `(item_id, revision)`, foreign key on). The handoff bytes are stored as a BLOB in the same transaction as the item. The denormalised `profile_id`/`title` are updated on each update.
- **Archive consistency.** `CHECK ((archived_at IS NULL) = (archive_reason IS NULL))` and the `archive_reason` enum hold.
- **Delivery.** No path writes `delivered` outside INB-002.
- **Stale state.** An update raises `state_version`, so an archive or acknowledge made from an older view fails with `STATE_CONFLICT`, and a newer revision is never archived unseen. Acknowledge also needs `revision == content_revision`.
- **Event order.** Writers are serialized, so sequence numbers become visible in commit order and a poller cannot skip a gap.
- **Migrations.** They are serialized in one IMMEDIATE transaction, and a newer schema is refused (tested).
- **WAL.** WAL is enabled only on an engine with the reset fix.
- **Handoff capture.** The file is checked for size before and after the read, and for valid UTF-8 and no NUL. Oversize input is refused, never truncated.

Findings: none beyond F2 and F4. One observation in Note N2.

### INB001-R1-F7 Minor: C1 control characters pass validation
- **Where:** `src/core/submission.ts:67-68`
- **Scenario:** a title or summary contains U+009B (CSI, a terminal escape introducer) or U+0085.
- **Expected:** spec §5.1 says to reject NULs and inappropriate control characters.
- **Actual:** only C0 and DEL are rejected, so C1 is stored. The mod strips control characters when rendering (decisions.md), which limits the harm. Any other client, such as a raw `list` in a terminal, would pass them through.
- **Impact:** low.
- **Smallest fix:** add `\u0080-\u009F` to both patterns.

### INB001-R1-F8 Minor: a transient lock on the handoff file is reported as permanent bad input
- **Where:** `src/core/submission.ts:209-218`
- **Scenario:** on Windows, the producer's handoff is briefly locked when `submit` runs, for example by antivirus or a writer that has not closed the file yet. The result is `EBUSY` or `EPERM`.
- **Expected:** a retryable error, so the producer tries again.
- **Actual:** `INVALID_ITEM`, `retryable:false`, exit 2. Also, `readFileSync` at line 218 sits outside the try block, so an error there becomes `INTERNAL`, exit 1.
- **Impact:** low. A producer that follows `retryable` gives up on a valid item.
- **Smallest fix:** map `EBUSY`/`EPERM`/`EACCES` from stat or read to a retryable error (for example `INVALID_ITEM` with `retryable: true`, or a new code), and move the read inside the try.

## Notes

- **N1. The producer surface is not documented.** The spec (line 277) asks for the producer surface to be kept apart from user and internal commands. The CLI usage line lists all commands together, and `skill/` is still empty. The companion-skill task should name the producer commands: `submit`, `update`, `get`, `list`, `events`, `status`.
- **N2. `get` and `list` read item, revision and attempt id without a shared read transaction.** See `inbox.ts:243-267`, `:297-307` and `:582`. The returned `blocking_attempt_id` can come from a slightly different moment than `state_version`. Every write re-checks under its own transaction, so nothing is corrupted. Wrapping the reads in `.deferred()`, as `events`/`status` already do, would make the view consistent.
- **N3. `acknowledge` does not call `assertNoBlockingAttempt`.** This is safe today because only actionable items can have attempts (`attempts.ts:140`), and acknowledge is informational-only.
- **N4. Spec §8 says `get` returns an attempt summary; today it returns `blocking_attempt_id` only.** I assume the fuller summary belongs to INB-002 or a later task.
