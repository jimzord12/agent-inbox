## Findings

### INB002-R2-F1 — Material — another attempt's opening prompt is classed as an ordinary prompt and would pass the guard
- **Where:** `src/core/attempts.ts:480` and `:486`
- **Scenario:**
  1. Attempt A's session (live, or delivered or abandoned) receives a prompt starting with `[agent-inbox att_B] Read the handoff packet at …`. This is attempt B's opening prompt. It arrives because B's worker targeted the wrong pane, for example a reused pane id, which spec §10.3 explicitly warns about.
  2. A's `UserPromptSubmit` bridge calls `acceptPrompt` for attempt A.
  3. `protocol` is computed only against `${OPENING_PREFIX}${a.id}]`, so it is `false`.
  4. Probe result:
     - live A: `{"ok":false,"protocol":false,"code":"NOT_PROTOCOL"}`
     - abandoned A: `{"ok":false,"protocol":false,"code":"ATTEMPT_CLOSED"}`
- **Expected:**
  - Spec §9.2 step 6 says the guard "must fail closed for the inbox protocol prompt when validation fails".
  - Spec §10.3 says the prompt guard is the second identity check against wrong-session delivery.
  - Any `[agent-inbox ` prompt that is not this attempt's accepted opening prompt should come back with `protocol: true` and a refusal.
- **Actual:**
  - Under the hook contract the code defines (block when `protocol`, pass otherwise), INB-005 would let B's prompt through.
  - Session A would then read B's packet.
  - B gets no false delivery: B's bridge never sees an acceptance, and A's `Stop` rejects B's marker. The damage is that the context lands in the wrong session.
- **Impact:** the core's half of the second wrong-session defence is disabled for cross-attempt prompts. That is the case it exists for: the spec's Blocking category "context sent to the wrong session", once the worker-side check has failed.
- **Smallest fix:**
  - Set `protocol = prompt.trimStart().startsWith(OPENING_PREFIX)`.
  - Refuse a protocol prompt whose id is not `a.id` with a code such as `WRONG_ATTEMPT` (or `PROMPT_MISMATCH`).
  - Keep `ATTEMPT_CLOSED` with `protocol: true` for any inbox-prefixed prompt.
  - Add one unit test with two attempts.

### INB002-R2-F2 — Minor — `finishOp` can re-finish an op, which lets `fail` bypass the F3 guard and desyncs `prompt_state`
- **Where:** `src/core/attempts.ts:349-360`, with `:363-372` and `:579-586`
- **Scenario A** (probe P2):
  1. `beginOp(dispatch_prompt)`, then `finishOp(uncertain)`. `prompt_state` becomes `uncertain`.
  2. A reconcile step calls `finishOp(dispatch_prompt, "failed")`.
  3. The op row becomes `failed`, but `prompt_state` stays `uncertain`, because the update only fires from `started`.
  4. `clearFailedOp` correctly refuses.
  5. `fail()` now succeeds (`status failed`) and releases the item, although the prompt state says the submission may have happened.
- **Scenario B** (probe P3):
  1. `finishOp(failed)`, then `finishOp(confirmed)`, then `clearFailedOp`.
  2. `prompt_state` resets to `none`, but the `confirmed` row stays, because the DELETE only removes `failed` rows.
  3. `beginOp` then returns `confirmed`, and the worker believes it dispatched.
  4. This fails closed (`acceptPrompt` answers `NO_DISPATCH`), but the attempt is left inconsistent.
- **Expected:** an op leaves `started` once, or leaves `uncertain` once through reconcile. `fail` respects an unresolved `prompt_state`.
- **Impact:** low today, since no worker exists yet. It matters for INB-008 and INB-009 reconcile, which will call exactly these transitions. No duplicate prompt is possible.
- **Smallest fix:**
  - `finishOp` only updates rows whose state is `started` or `uncertain`. Refuse otherwise.
  - When a `dispatch_prompt` moves from `uncertain` to `failed`, set `prompt_state = rejected`, because the caller is asserting a definitive rejection. Or refuse that move, and leave `uncertain` resolvable only by bridge acceptance or by abandon.
  - The `fail` guard also refuses when `prompt_state` is `started` or `uncertain`.
  - `clearFailedOp` sets `prompt_state = none` only when its DELETE removed a row.

### INB002-R2-F3 — Minor — the new tests write Windows paths with single backslashes
- **Where:** `test/unit/attempts.test.ts:307, 310, 323, 364, 379, 383, 395, 397, 398`
- **Problem:** in a string literal, `"C:\p.md"` is `"C:p.md"`, and `"C:\elsewhere"` is `"C:elsewhere"`.
- **Impact:** the tests still pass and prove their point, but they no longer exercise the Windows path shapes their text suggests. The WRONG_CWD case compares against a drive-relative string.
- **Smallest fix:** use `"C:\\p.md"`, as the older tests do.

### INB002-R2-N1 — Note — `last_rejection` is never cleared
- **Where:** `src/core/attempts.ts:391-395` (`resume`) and `:413-422` (`commitDelivery`)
- **Probe P4:** a delivered attempt still shows `last_rejection: {stage:"bind", reason:"session id does not match…"}`.
- **Why it matters:** INB-013 shows `last_rejection` beside the attempt's status, so the owner will see this stale reason on a delivered attempt.
- **Suggested fix:** clear `last_rejection` on resume or on success, or have the UI show it only while the attempt is blocking.

### INB002-R2-N2 — Note — a valid receipt from the original session is still captured while the attempt is blocked for "session replaced"
- **Where:** `src/core/attempts.ts:501-531` (`bridgeRow` allows `blocked`)
- **Probe P4:**
  1. The re-bind fails, which drops the candidate.
  2. A `Stop` hook call for the *original* session id with a valid marker sets a new candidate.
  3. `resume`, then `commitDelivery`, ends in `succeeded`.
- **Assessment:** I accept this. The receipt comes from the bound session id and the correct challenge, so it shows that conversation holds the handoff, for example after `/resume` back to it. Spec §9.2 allows a late valid candidate to be reconciled. `Stop` hooks complete before the next input, so a stale `Stop` after `/clear` should not occur. Record this reasoning in INB-005 and INB-008.

### INB002-R2-N3 — Note — `acceptPrompt` throws `NOT_FOUND` for an unknown attempt id
- **Where:** `src/core/attempts.ts:478`
- **Probe P5:** an unknown id (store reset or deleted) throws `NOT_FOUND`.
- **What INB-005 must do:** the hook must still let ordinary prompts through in that case, and block only inbox-prefixed ones.
