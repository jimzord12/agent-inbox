## Lenses

**1. Product fit and wiring.** Pass. The hook process still goes `main.ts` -> `safeHandle` -> `handle` -> `Attempts`. The busy path is reached only from `safeHandle` for `stop` on `STORE_BUSY`. AC1-AC5 still hold; nothing in this round touches settings, SessionStart or the prompt guard.

**2. Correctness and edge cases.** Pass.
- `stopWhileBusy` now gates on `parseReadyMarker(message).ok`, the same parser `captureReceipt` uses (`attempts.ts:520`). So the bridge keeps exactly the replies the store could accept: marker on the last non-empty line, right fields and types, non-empty orientation. Round 2's N3 (a marker not on the last line kept anyway) is gone.
- CRLF replies: `parseReadyMarker` normalises `\r\n`; the message is saved unchanged, so replay sees the same input as the live hook.
- Size: the saved message is bounded by `MAX_INPUT_BYTES` (8 MB) in `main.ts`; a larger input becomes `{}` and saves nothing.

**3. Data integrity (lead).** Pass.
- The pending file now holds the whole `last_assistant_message`. Replaying it through `captureReceipt` gives the same result as the original Stop would have: the test replays the saved content and gets `{ ok: true }` plus `receipt_candidate = true`.
- No false-delivery path is added. The pending file is only evidence: on replay `captureReceipt` still checks capability, revoked or closed state, bound session id, accepted prompt, attempt, item, revision, packet hash and challenge. A forged or stale file cannot pass those checks without the capability and challenge, which only the attempt's own folder and store hold.
- The parse gate cannot drop a valid receipt: anything the gate refuses, `captureReceipt` would refuse with the same parser.
- Replay is idempotent (`if (!a.receipt_candidate_json)`), so a reconcile that replays twice, or replays after a late successful Stop, records one candidate.

**4. Contracts and privacy.** Pass.
- Hook output on the busy path is unchanged: exit 0, empty stdout and stderr (test).
- The pending file holds attempt id, session id, the reply and a timestamp; never the capability (test asserts it). It now also holds the orientation text. That text is the session's own summary of the packet and sits in `<home>\attempts\<id>\` beside `bridge.json`, which already holds the capability, so its exposure is no wider than what the folder already has.
- The INB-009 contract note (line 45) says the file holds the whole reply and must be validated like any bridge evidence; that matches the code. See N1 for the older line above it.
- **Privacy:** none found.

**5. Tests and evidence.** Pass. The busy test runs the real hook process against a held `BEGIN IMMEDIATE` lock, then replays the saved reply through `captureReceipt`. Reverting R2-F1 (keeping only marker lines) makes that replay return `no orientation before the marker`, so the test fails. Removing the parse gate would not fail a test (a marker-less busy Stop has no direct test); low value, the store re-checks anyway.

**6. Failure handling (lead).** Pass.

| Path | Bound | Outcome |
|---|---|---|
| Stop, store write-locked throughout | 2 opens x 2 s | exit 0, whole reply saved if it parses |
| Stop, worst case (each wait almost succeeds) | 4 waits x 2 s, about 8 s plus start-up | inside 15 s; the comment now says this (R2-F2) |
| Stop, busy and reply not a receipt | same waits | exit 0, nothing saved (correct: an ordinary turn) |
| Stop, retry fails with a non-busy error | immediate | exit 0, nothing saved |
| Pending write fails | immediate | swallowed, exit 0; attempt recoverable by abandon |

- The retry cannot repeat a side effect: `STORE_BUSY` means the IMMEDIATE transaction never committed, and the write is idempotent.
- `main.ts` deadline (10 s) cannot fire mid-handler, because the store calls are synchronous; the 15 s settings timeout stays the outer bound, with margin over the 8 s worst case.

**7. Simplicity and ownership.** Pass. Reusing `parseReadyMarker` instead of a local line filter removes a second, looser definition of "a marker", and the bridge still writes only the fallback file, never the store outside `Attempts`.

**8. Repository and docs.** Pass with a note. The INB-005 note records both dispositions; the INB-009 note was extended. Commit subject follows the convention.
