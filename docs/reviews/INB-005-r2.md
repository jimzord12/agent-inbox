## Lenses

**1. Product fit and wiring.** Pass. The hooks still reach `Attempts` through `handle`; all three round 1 fixes are wired into the real hook process (`main.ts` passes `bridgePath`; `handle` opens with `existingOnly` and the 2 s busy timeout). AC1-AC5 still hold.

**2. Correctness and edge cases.** Pass with a note.
- `existingOnly` is used only by `src/bridge/hooks.ts:79`. The CLI (`src/cli/main.ts:212`), `doctor` (`src/cli/doctor.ts:17`) and the test helper construct `Inbox` without `store`, so they keep `ensureHome` and `create: true`. No regression for other callers.
- Skipping `ensureHome` skips only `mkdirSync`; the home string comes from `bridge.json`, written by the worker with an absolute home, so no path normalisation is lost.
- `PRAGMA journal_mode = WAL` on an existing WAL store is a no-op and takes no lock: the probe's open under a held write lock waited only on the migrate transaction (STORE_BUSY after 2227 ms), and the store info reported `wal`.
- A missing `inbox.db` in an existing home gives `STORE_ERROR`, nothing created (probe). Bun reports `SQLITE_CANTOPEN`, so the explicit branch in `db.ts:36` fires. The same code also covers a permission or locked-directory failure, which is then worded "does not exist"; cosmetic.
- N2 fix: the `blocked` refusal sits before the binding checks, so a startup mismatch now refuses with `ATTEMPT_BLOCKED` instead of `NOT_BOUND` (round 1's table). Both are refusals; nothing depends on the code.

**3. Data integrity (lead).** One Material finding.
- No new path can mark an attempt delivered or accept a prompt it should not: `existingOnly` only removes creation, the busy timeout only shortens waits, and the blocked guard only refuses more.
- The pending-receipt file is where the F2 fix fails: it drops the orientation text that `parseReadyMarker` requires, so the evidence it was meant to keep cannot be turned back into a receipt candidate (F1 below).
- **Uncertain attempts still accept (author's choice): sound.** `uncertain` means the dispatch outcome is unknown. A prompt that passes every other check (bound session, cwd, exact opening prompt, `prompt_state` started or uncertain) is exactly the evidence that the dispatch landed. Refusing it would turn a provable delivery into a forced abandon and re-send. A superseding retry must first reconcile and close the old attempt (INB-008/009), after which `closed()` refuses. `blocked` differs: the owner was asked to act, so refusing is right.

**4. Contracts and privacy.** Pass, apart from the pending-file contract in F1.
- Hook output is unchanged: the busy Stop path exits 0 with no output (test and probe).
- `receipt-pending.json` holds attempt id, session id, the marker line (which carries the challenge) and a timestamp, never the capability (test asserts it). It sits in `<home>\attempts\<id>\` beside `bridge.json`, which already holds the capability, so it is no less private than what is already there. The challenge only matters to a process that can also read `bridge.json`.
- `ANTHROPIC_CUSTOM_HEADERS` added, with a test.
- **Privacy:** none found.

**5. Tests and evidence.** Pass with a gap. New tests: missing home (no store, protocol prompt `STORE_ERROR`), blocked attempt refuses, busy store gives a quick `STORE_BUSY` block and a pending file, custom-headers name. Deleting any of the fixes fails a test. The busy test asserts `last_assistant_message.startsWith(READY_MARKER)`, which codifies the F1 defect instead of checking that the saved content still parses as a receipt.

**6. Failure handling (lead).** One Material (F1), one Minor (F2).

| Path | Measured / derived bound | Outcome |
|---|---|---|
| Prompt, store write-locked | open waits 2 s, then `STORE_BUSY` (probe 2227 ms) | protocol prompt blocked with `STORE_BUSY`, ordinary passes |
| Stop, store write-locked throughout | 2 opens x 2 s (probe 4541 ms total) | exit 0, pending file written |
| Stop, worst case (lock churns so each wait almost succeeds) | 4 waits x 2 s = about 8 s plus about 0.1 s start-up | still inside 15 s; the comment says 6 s (F2) |
| Stop, store missing or other error | immediate | exit 0, nothing recorded (by design) |
| Pending write fails | immediate | swallowed, exit 0; attempt recoverable by abandon |

- The retry cannot repeat a side effect: `captureReceipt` runs in one IMMEDIATE transaction, so `STORE_BUSY` means nothing committed, and the write is idempotent anyway (`if (!a.receipt_candidate_json)`).
- The retry cannot exceed Claude's 15 s cancel in WAL mode. In rollback-journal mode (only on an engine without the WAL fix) a commit can add a busy wait for readers; still far from 15 s in practice (N1).

**7. Simplicity and ownership.** Pass. The pending file is written by the bridge, not the core, which is right: it exists for the case where the core's store cannot be written. `OpenOptions` is a small, opt-in addition to `openStore`.

**8. Repository and docs.** Pass with F1's consequence. Dispositions are on the task; N1 routed to INB-006 and INB-009 got the pending-file contract. That INB-009 note says "replay it through captureReceipt", which cannot succeed with the file as written (F1). The INB-005 note says "worst case about 6 s" (F2).

## Findings

### INB005-R2-F1: Material. The pending receipt drops the orientation, so its prescribed replay always fails

- **Where:** `src/bridge/hooks.ts:134-142` (filter keeps only lines starting with `INBOX_READY_V1`); `src/core/attempts.ts:699-700` (`parseReadyMarker` refuses a message with no text before the marker); the INB-009 note ("Reconcile must replay it through captureReceipt").
- **Scenario:**
  1. The session ends its opening turn with orientation text plus a valid marker.
  2. The worker holds the write lock for more than 2 s, twice.
  3. Stop writes `receipt-pending.json` with only the marker line.
  4. Reconcile replays it through `captureReceipt`.
- **Expected:** the replay records the receipt candidate, as the original message does.
- **Actual:** the probe's replay returned `{ ok: false, reason: "no orientation before the marker" }`, with no candidate. The same original message gives `{ ok: true }`. The replay also writes a misleading `last_rejection_json`, because the message contains the marker.
- **Impact:** the round 1 F2 fix does not deliver its purpose. A valid acknowledgment lost to a busy store still ends with abandon and a re-send to a fresh session, now after a misleading rejection. No false delivery. `orientation_chars` is part of the receipt, so the orientation length is needed even if the text is not.
- **Smallest fix:** save the whole `last_assistant_message` (it is already bounded by `MAX_INPUT_BYTES`), or at least keep it when a marker line exists. Or save the parsed receipt from `parseReadyMarker` (it has `orientation_chars`) and have reconcile validate that against the row. In the test, assert that the saved content passes `parseReadyMarker` or a `captureReceipt` replay, not only `startsWith`. If the whole message is kept, check that the INB-009 note still matches.

### INB005-R2-F2: Minor. The stated worst-case bound undercounts the Stop retry

- **Where:** `src/bridge/hooks.ts:35-37`; the INB-005 task note ("worst case about 6 s").
- **Scenario:** in `stopWhileBusy` the retry calls `handle` again, which reopens the store (one more migrate wait) before the write (one more wait).
- **Expected:** the comment states the real bound.
- **Actual:** the comment counts three waits (6 s). The path has up to four 2 s waits: open, write, reopen, write. That is about 8 s plus start-up. This is still inside 15 s, so behaviour is fine.
- **Impact:** low. Someone raising `HOOK_BUSY_TIMEOUT_MS` from the comment's arithmetic would get less margin than they think.
- **Smallest fix:** say "four waits, about 8 s" in the comment and the note. Or reuse the open connection for the retry.

## Notes (do not block)

- **N1. Rollback-journal stores.** On an engine without the WAL fix the store runs in `DELETE` mode. There a commit can also wait on readers, up to `HOOK_BUSY_TIMEOUT_MS` per transaction. Readers are short, so this is theoretical, and this machine runs WAL (3.53.4). Worth a line in the comment if F2 is touched.
- **N2. One pending file per attempt, last write wins.** A second busy Stop with a marker overwrites the first. That is fine as long as reconcile validates whatever it finds. A busy Stop with no marker leaves an older file in place, so reconcile must not treat the file's presence as fresh. The fixed `.tmp` name is safe, since one session runs per attempt.
- **N3. Marker not on the last line.** The pending filter keeps a marker line anywhere in the message, but `parseReadyMarker` accepts it only on the last line. With the F1 fix (keep the whole message) this disappears. If only marker lines are kept, the filter keeps candidates that can never parse.
