## Lenses

**1. Product fit and wiring (lead).** Every spec §8 command phase 1 needs is wired in `src/cli/main.ts`: submit, update, get, list, events, mark-read, mark-unread, acknowledge, snooze, unsnooze, archive, restore, status, doctor. Each reaches the core and behaves as the spec says (end-to-end run above). `open`, `attempt`, `retry`, `abandon` and `focus` are rightly absent; they belong to INB-006.

The two consumers fit together:
- **Producers** get idempotent submit, a revision-guarded update, get, list, events with a safe cursor, and status.
- **The mod and worker** get user commands guarded by `state_version` or the displayed revision, plus an in-process `Attempts` API whose views hide capability, challenge and packet bytes (`attempts.ts:69-100`).

Gaps for the consumers are recorded as Notes N1 and N2, both already routed to later tasks.

**2. Correctness and edge cases.**
- Time zones: all times are stored as UTC fixed-width ISO strings. Offset-qualified input is required, and impossible fields are refused.
- DST: does not apply, because only offset-qualified times are accepted.
- Windows paths with spaces or Unicode work for both the handoff and the cwd.
- Duplicate submissions and racing state changes give exactly one winner.
- Sibling paths are consistent: `update` and `submit` share capture and validation.

Edge findings: a lost-response update retry (F1), and a year-10000 rollover (N4).

**3. Data integrity (lead).**
- Nothing is ever deleted. Revisions are immutable, keyed `(item_id, revision)`, and hold the exact handoff bytes in SQLite. Foreign keys are on.
- Each state change and its event share one IMMEDIATE transaction.
- A partial unique index allows at most one blocking attempt (`migrations.ts:320`).
- Delivery is one transaction (`attempts.ts:405-441`): receipt, `succeeded`, archive(delivered) and the events. It needs an in-progress attempt, a binding, an accepted prompt, a receipt candidate, and an unchanged, unarchived item.
- Every worker write checks fencing (`attempts.ts:562-574`).
- An accepted prompt can no longer be marked `failed`.
- A restored delivered revision cannot reopen silently (`ALREADY_DELIVERED`).
- Event sequence numbers are allocated under SQLite's single writer, so pollers never see them out of order. The events read runs in one snapshot.

I found no path that loses, corrupts or falsely delivers an item, revision, attempt or event.

**4. Contracts and privacy.**
- The envelope is exactly `{api_version, ok, data|error{code,message,retryable,details?}}`. stdout carries one line. Exit codes are 0 / 1 / 2 as specified.
- Error codes match spec §8, plus documented additions: `HANDOFF_UNAVAILABLE`, `STORE_INCOMPATIBLE`, `STORE_ERROR`, `INVALID_ARGUMENT`.
- Events carry no handoff text, which is tested.
- Privacy check: none found.

**5. Tests and evidence.**
- Real SQLite throughout. The fake clock is the only mock, and the CLI tests spawn real processes.
- Deleting the `fail`-after-accept guard or the delivery clearing would fail the new tests.
- Deleting the `handoffReadError` call inside `captureHandoff` would not fail any test (F2).

**6. Failure handling.**
- A busy store gives `STORE_BUSY`, retryable, with a bounded 5-second busy timeout.
- A newer schema is refused (`STORE_INCOMPATIBLE`).
- Bad JSON or input exits 2. A locked handoff is retryable.
- The intent log never repeats a started or uncertain op. An uncertain dispatch can never become `failed`.
- One note on retry semantics for a permanently denied file (N3).

**7. Simplicity and ownership.** Core is the only database writer; the CLI goes through `Inbox`, and `Attempts` writes through `inbox.write`. No unasked scope inside M1. `setup-profiles` and `doctor`'s Herdr section belong to INB-004 and were built there.

**8. Repository and docs.** The "Build decisions" section in `decisions.md` matches the code. INB-021's notes match the commit. Commit scope and subject follow the convention. One stale naming example (N5).

## Findings

### M0-R1-F1 (Minor): a retried update after a lost response returns `REVISION_CONFLICT` although its content already landed

- **Where:** `src/core/inbox.ts:226-228`
- **Scenario:**
  1. A producer sends `update ITEM --if-revision 1` with payload P.
  2. The update succeeds and becomes revision 2, but the response is lost (crash, timeout).
  3. The producer retries the same command.
- **Expected:** the retry is recognised as already applied and returns `changed:false`, as an identical update would be. Spec §6.3 calls an identical update a no-op.
- **Actual:** `REVISION_CONFLICT`, `retryable:false`, `details.content_revision: 2`. I reproduced this through the CLI.
- **Impact:** the producer cannot tell "my update landed" from "someone else changed it". It must `get` and compare the payload itself. A naive producer reports a spurious conflict. No data is harmed.
- **Smallest fix:** in `update`, compare the new content hash with the current revision's hash before the `ifRevision` check, and return `changed:false` when they match. Alternatively, document get-and-compare after `REVISION_CONFLICT` in the producer skill (INB-015).

### M0-R1-F2 (Minor): the locked-handoff test covers the error mapping, not its wiring into capture

- **Where:** `test/unit/core.test.ts:324-333`; `src/core/submission.ts:224-226`
- **Scenario:** `captureHandoff` is changed so it no longer calls `handoffReadError`, for example by reverting to the old inline `INVALID_ITEM` logic.
- **Expected:** a test fails. The carried R2-F2 asked for a test of the locked path.
- **Actual:** the test calls `handoffReadError("EBUSY")` directly. Its only `submit` case uses a missing file, which gives `INVALID_ITEM` either way. The real path works: I confirmed it live with a `FileShare.None` lock, which gave `HANDOFF_UNAVAILABLE` and exit 1.
- **Impact:** a future regression of the producer-retry signal would go unnoticed.
- **Smallest fix:** in `core.test.ts`, use `spyOn` on `fs.readFileSync` (or `statSync`) to throw an `EBUSY` error once. Then assert that `submit` returns `HANDOFF_UNAVAILABLE`, that `retryable` is true, and that no item exists. Or record why not.

## Notes

- **M0-R1-N1:** `status.change_token` is the latest event sequence (`src/core/inbox.ts:486`). Attempt-only progress does not move it: phase, prompt acceptance, receipt candidate, availability, last rejection. In my probe the token was unchanged after bind, accept and dispatch-confirmed. That is fine for list refresh, since items only change through events. The attempt view (INB-013) must poll `attempt get`, not the token.
- **M0-R1-N2:** `get` exposes only `blocking_attempt_id`; there is no attempt or delivery summary (`src/core/inbox.ts:244-268`). Spec §8 asks for one. Through the CLI, a restored, already-delivered item looks like any active item until `open` answers `ALREADY_DELIVERED`. This was already accepted in INB-001 (N3/N4) and routed to INB-006. Recorded here so the M2 loop checks it.
- **M0-R1-N3:** `EPERM` and `EACCES` count as transient (`src/core/submission.ts:210`), so a file whose access control list permanently denies reading answers `retryable:true` forever. This is an accepted decision (`decisions.md`). The producer skill (INB-015) should tell producers to cap their retries.
- **M0-R1-N4:** `parseOffsetTime` accepts `9999-12-31T23:30:00-01:00`. In UTC that is year 10000, which `toISOString` writes as `+010000-…`. That string compares below the present, so `snooze` refuses it as "must be in the future". The time is refused, so nothing is corrupted (`src/core/clock.ts:11-26`). No action needed.
- **M0-R1-N5:** `docs/reviews/README.md:1` gives `m-1-r1.md` as the milestone example, but milestone M1's id is `m-0`, and `practices/review.md` uses `m-<n>`. The example could make the next author name M1's report as M2's. Use `m-0-r1.md` as the example.
