## Findings

### INB009-R2-F1 - Minor - The stale-receipt guard trusts a field that later writes overwrite or clear

- **Where:** `src/worker/reconcile.ts:91-95`. It reads `last_rejection_json`, which `src/core/attempts.ts:505` (prompt refusal), `:537` and `:554` (receipt refusals) overwrite, and which `:411` (`resume`) and `:441` (`commitDelivery`) set to null.
- **Scenario A (probe PA):**
  1. The session acknowledges. Stop meets a busy store, and the bridge writes `receipt-pending.json`.
  2. `/clear` triggers a bind rejection: the candidate is dropped and the attempt is blocked.
  3. Before any read, a protocol-prefixed prompt is submitted in the cleared session, for example the opening prompt resent from history. It is refused `ATTEMPT_BLOCKED`, and `last_rejection_json` becomes stage `prompt`.
  4. The next reconcile replays the stale file: `replayed 1, receipt_candidate true`.
- **Scenario B (probes PC and PB):**
  1. Same steps 1 and 2.
  2. The user runs `retry` while another connection holds the store, and an older lapsed in-progress attempt sorts first. Reconcile meets STORE_BUSY on that one and breaks, so this attempt's stale file is never looked at (PC: `stale file still there true`).
  3. The retry worker starts, claims once the lock lifts, and `resume` clears `last_rejection_json`.
  4. The next reconcile replays the file: `resume true, replayed 1, receipt_candidate true`.
- **Expected:** the round 1 disposition: "a receipt the bridge dropped on purpose (e.g. /clear) cannot come back".
- **Actual:** it comes back whenever a later write replaces or clears the bind rejection before a reconcile reaches the file.
- **Impact:** low. The same layer round 1 F1 named is lost, but only on narrower paths: an extra coincidence is needed before the next read, and the mod's polling shrinks that window. A false delivery still needs Herdr to report the original session id in the pane, and Herdr's own SessionStart hook updates that id after `/clear`.
- **Smallest fix:** make the drop durable at its source. Either remove `receipt-pending.json` in the bind-mismatch path (the hook knows the bridge directory), or record a `receipt_dropped_at` that `resume` and later rejections do not touch, and compare `written_at` against it. Add a test: stale file, then `/clear`, then a refused protocol prompt (or a `resume`), then reconcile, expecting no candidate.

### INB009-R2-F2 - Minor - Two round 1 fixes are not pinned by any test

- **Where:** `src/worker/reconcile.ts:61` (the `break` on STORE_BUSY, round 1 F5); `src/worker/worker.ts:290` (the `herdr_session` guard, round 1 N3).
- **Scenario:** deletion probes M1 (`break` changed to `continue`), M13 (busy swallowed without break) and M8 (guard removed) all leave 257 tests passing. The test "a busy store keeps the pending receipt for the next pass and ends the pass at once" uses one attempt, so it cannot tell `break` from `continue`, and it checks no timing.
- **Expected:** a test fails if the bounded wait or the server guard regresses. The task notes record both as fixed.
- **Actual:** both can regress silently. M1 brings back the N × busy-timeout stall on every mod poll.
- **Smallest fix:**
  - Busy store: hold the lock with two or three lapsed attempts that have ops recorded, and assert that the pass returns in under two busy timeouts (or that later attempts are untouched).
  - Server guard: a lost-tab-create attempt whose `herdr_session` differs from `config.herdr.socket_path`, and assert that `candidate_tabs` is empty and the fake saw no `tab list`.

### INB009-R2-F3 - Minor - A persistent replay error silently skips the attempt's lapsed-lease handling on every pass

- **Where:** `src/worker/reconcile.ts:38` (replay shares the per-attempt `try` with the lapsed-lease branch) and `:58-62` (the error is swallowed with no trace).
- **Scenario (probe PF):** an in-progress attempt with a lapsed lease and ops recorded, plus a `receipt-pending.json` that cannot be removed (a non-empty directory in the probe; a persistent `EPERM` in practice). Two reconcile passes both return `marked_uncertain: []`, and the attempt stays `in_progress` with an expired lease indefinitely. Nothing is logged.
- **Expected:** the round 1 F4 intent: skip only the failing housekeeping step, and leave a trace.
- **Actual:** the whole attempt is skipped, and the user sees "in progress" with no hint why.
- **Impact:** low. `retry` still reconciles through the worker, and the item stays recoverable.
- **Smallest fix:** wrap `replayPending` in its own try so the lapsed-lease branch still runs. Write one line to the attempt's `worker.log` (or stderr) when a non-busy error is swallowed.

## Notes

- **N1 (Note).** `written_at` is compared as a string. A non-`Z` or malformed value misorders: probe PG replayed `"9999"` and `"2026-10-22T10:00:00+01:00"`, the latter equal to the rejection instant. Only the bridge writes this file, and it always writes `toISOString()`, so this only matters for hand-edited files. `captureReceipt` still checks everything else. A backward clock step between the Stop and the `/clear` (NTP correction) could likewise let a stale file through; F1's durable fix would remove both. `Date.parse` on both sides would harden the comparison.
- **N2 (Note).** If STORE_BUSY hits after `claim`, the `finally` release can itself throw STORE_BUSY, which is then caught and breaks the pass. Reconcile's 30 s lease stays live, so an immediate `retry` answers `started: false`. This happens only under a busy store and clears on its own in 30 s.
- **N3 (Note).** Deletion probes M3 (busy replay returns false) and M7 (`>=`) survive as equivalents (see lens 5). No test is needed.
- **N4 (Note).** The test title "...ends the pass at once" claims more than the test asserts (F2).
