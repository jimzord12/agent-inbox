## Findings

### M1-R2-F1 — Minor — two of the three guards on the dialog focus exception have no test

- **Where:** `src/worker/focus.ts:49` (`target.status !== "succeeded"` and `info.pane_id === target.herdr.pane_id`); test `test/unit/worker.test.ts:1110-1122`.
- **Scenario:** a later edit drops either condition. Without the status guard, a delivered attempt whose alias still exists with no session id would be focused instead of recorded `unknown`; without the pane guard, the alias reported in another pane would be focused.
- **Expected vs actual:** expected a test to fail for each guard, since the brief names "never a delivered attempt" and "never another session" as the exception's limits. Actual: deleting either one leaves 287 pass, 0 fail. The behaviour on head is correct (probes P1, P2).
- **Impact:** low; focus carries no context, so the worst regression is focusing the wrong pane or skipping an availability record, but the guard could vanish unnoticed.
- **Smallest fix:** two asserts in the existing test: a delivered attempt with `session = null` in its own pane is refused; a dialog-held attempt whose fake agent's `pane_id` is changed is refused.

## Notes

- **M1-R2-N1 — the exception is wider than "blocked".** It applies to any blocking attempt (`in_progress`, `blocked`, `uncertain`) with no session id in its own pane, e.g. a user focusing while Claude is still booting. Spec §10.2 names a blocked startup; the wider case is still the attempt's own alias and pane with no context sent, so acceptable. Worth one line in the `focus.ts` comment if it is kept on purpose.
- **M1-R2-N2 — `availability` on the starting path.** The response carries the stored value (by default `unknown`, P3) next to `focused: true`. The mod (INB-014) should key on `starting` and not render "unknown" for a session it has just focused.
- **M1-R2-N3 — untested defence in depth.** `watchBlockedStart` requires a session id before lifting the dialog block (`worker.ts:381`), and the dispatch step's rethrow (`worker.ts:435`) has no test of its own (the M3 test covers `start_agent`). Neither deletion is caught, but `verifyTarget` still blocks dispatch without the attempt's own session, and the M3 reviewer owns the rethrow.
- **M1-R2-N4 — the wait-loop replay swallows every error** (`worker.ts:462-466`), including non-store ones, unlike the rethrow rule just adopted for Herdr steps. No M2 effect (a failure only delays to the next poll or the receipt timeout); M3's call.
