### INB001-R2-F1 Minor: the CLI filter test does not tell apart `--kind`, `--unread` or `--producer`
- **Where:** `test/unit/cli.test.ts:145-157`
- **Scenario:** every item in the test is an informational, unread item from `example.reporter`. Suppose the flag mapping for `--kind`, `--unread` or `--producer` broke in `main.ts`, for example through a misspelled key, so the flag is silently ignored.
- **Expected:** the round-1 F5 fix says "test the CLI flag wiring". A dropped filter should fail a test.
- **Actual:** with any of those three filters ignored, every assertion still holds. Only `--profile nobody` and the cursors discriminate.
- **Impact:** low. A regression in a producer-facing filter (`events --producer`) would pass the gate, and a producer would then receive other producers' events.
- **Smallest fix:** submit one actionable item from `example.script` beside the informational ones. Then assert that `list --kind informational` excludes it and `events --producer example.reporter` excludes its event. Optionally, mark one item read and assert that `--unread` drops it.

## Lens 6. Failure handling

### INB001-R2-F2 Minor: a locked handoff file is reported as retryable bad input (exit 2), and the path has no test
- **Where:** `src/core/submission.ts:215-219`, `src/core/errors.ts:27`
- **Scenario:** `submit` runs while the handoff file is held by its writer or by antivirus, which gives `EBUSY`. Or the file is permanently unreadable for this user (`EACCES`/`EPERM` from an ACL).
- **Expected:** spec §8 says exit 2 means invalid usage or input. A transient condition is operational, so it should exit 1 and be retryable. A permanent permission denial should not invite endless retries.
- **Actual:**
  - The result is `INVALID_ITEM` with `retryable:true` and exit 2, because `INVALID_ITEM` is a usage code. A producer that branches on the exit code treats it as bad input; one that branches on `retryable` retries. The two signals disagree.
  - `EACCES`/`EPERM` are always retryable, including a permanent ACL denial. On Windows, though, these codes are also how sharing violations surface, so keeping them retryable is defensible.
  - No test exercises this branch.
- **Impact:** low. Producers get a contradictory signal on a rare path. The item is never corrupted, and nothing is stored on failure.
- **Smallest fix:** throw a code that is not a usage code for the transient case. `STORE_BUSY` is wrong semantically, so either add a code (for example `HANDOFF_UNAVAILABLE`, retryable, exit 1), or give `InboxError` a way for a retryable `INVALID_ITEM` to exit 1. Add a unit test that injects or stubs `EBUSY`. If this is accepted as is, record in the task notes that a retryable exit 2 is the intended contract.

## Notes

- **N1. The cursor-ahead check is a heuristic, not an epoch.** After a backup restore to seq 300, a consumer holding cursor 500 is refused only while the store's latest seq is below 500. If 200 or more events land before that consumer next polls, its cursor is accepted again, and events 301-500 are skipped silently. The same holds for a cursor taken from another home. A store id or epoch inside the cursor would close this. It is acceptable at MVP scale, and much better than round 1.
- **N2. The `attempts.ts:199` BOM decoding came in with INB-002 (`60de7c2`), and no test in this unit covers it.** The fix is the same one-liner as `inbox.ts:126`. Coverage belongs to INB-002's review: whether the packet hash or bytes are asserted with a BOM handoff.
- **N3. `submission.ts:225` still strips the BOM when decoding for the NUL check.** It is harmless, since that text is discarded. The comment at `inbox.ts:125` could mention that the capture-time decode is intentionally different, so a later edit does not "unify" the two the wrong way.
